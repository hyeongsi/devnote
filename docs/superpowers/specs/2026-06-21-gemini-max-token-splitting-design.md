# Gemini MAX_TOKENS 분할 생성 설계

## 배경

현재 `GeminiAiPostClient`는 게시글 계획을 만든 뒤 상위 섹션별 본문을 한 번에 생성한다. 섹션 응답이 `MAX_TOKENS`로 끝나면 더 짧은 프롬프트로 같은 섹션 전체를 한 번 다시 생성하지만, 재시도도 출력 한도에 도달하면 전체 게시글 생성이 실패한다.

긴 글의 품질을 유지하려면 전체 글자 수나 코드 예제 수를 강제로 제한하는 대신, 모델 호출 한 번이 담당하는 생성 범위를 작게 만들어야 한다.

## 목표

- 상위 섹션을 여러 개의 독립적인 하위 생성 단위로 나눈다.
- `MAX_TOKENS`가 발생한 생성 단위만 더 작은 단위로 재분할한다.
- 이미 `STOP`으로 완성된 생성 결과는 다시 호출하지 않고 보존한다.
- 전체 글 분량, 설명 깊이, 코드 예제 수를 고정된 숫자로 제한하지 않는다.
- 최종 Markdown의 목차 순서와 문맥 일관성을 유지한다.
- 실패 시 어느 섹션, 하위 단위, 분할 깊이에서 종료됐는지 로그와 예외에 남긴다.

## 제외 범위

- HTTP 요청을 작업 ID 기반 비동기 API로 변경하지 않는다.
- 중간 생성 결과를 데이터베이스에 저장하지 않는다.
- 서버 재시작 후 생성 작업을 복구하지 않는다.
- 관리자 화면의 생성 UI와 Nginx 설정을 변경하지 않는다.
- Gemini 사용량 제한이나 HTTP 429 재시도 정책은 이번 작업에서 변경하지 않는다.

## 접근 방식 비교

### 출력 토큰 상향

구현은 단순하지만 한계 도달 시 같은 문제가 반복되고, 요청 시간과 사용량이 함께 증가한다. 모델이 지원하는 범위 안에서 보조 설정으로 사용할 수 있지만 주 해결책으로 삼지 않는다.

### 잘린 응답 이어쓰기

부분 응답을 보존할 수 있지만 문장과 코드 블록 경계를 복원하기 어렵고, 중복 문단을 안정적으로 제거해야 한다. 불완전한 Markdown을 정상 결과로 취급할 위험이 있어 기본 전략으로 사용하지 않는다.

### 계층형 분할 생성

상위 섹션을 완결 가능한 하위 단위로 생성하고, 한 단위가 잘릴 때 그 단위만 재분할한다. 완성된 결과를 안전하게 보존하면서 전체 글의 깊이도 유지할 수 있어 이 방식을 채택한다.

## 생성 모델

### 게시글 계획

기존 상위 섹션 계획에 하위 생성 단위를 포함한다.

```text
Section
- key
- heading
- brief
- units[]

Unit
- key
- heading
- brief
```

계획 프롬프트는 섹션의 복잡도에 따라 필요한 만큼 하위 단위를 만들도록 요청한다. 짧은 섹션도 최소 하나의 단위를 갖는다. 고정 글자 수나 고정 코드 예제 개수는 계획 스키마에 넣지 않는다.

각 키는 게시글 내에서 고유하고 순서가 안정적이어야 한다. 상위 섹션 키와 하위 단위 키를 결합한 `contentKey`를 생성 결과 식별자로 사용한다.

### 생성 결과 트리

요청이 진행되는 동안 결과를 메모리의 순서 보장 트리로 유지한다.

```text
SectionResult
- section metadata
- ordered ContentNode list

ContentNode
- contentKey
- heading
- brief
- depth
- status
- markdown 또는 children
```

`STOP`으로 끝난 노드는 완성 노드가 되고 Markdown을 보존한다. `MAX_TOKENS`로 끝난 노드는 완성 결과로 저장하지 않고 자식 노드로 교체한다. 형제 노드와 다른 상위 섹션은 변경하지 않는다.

## MAX_TOKENS 처리

1. 하위 단위 하나를 Markdown으로 생성한다.
2. `STOP`이면 해당 결과를 완성 상태로 보존한다.
3. `MAX_TOKENS`이면 해당 단위의 제목과 목표를 입력으로 작은 JSON 분할 계획을 요청한다.
4. 원래 단위를 두 개 이상의 더 구체적인 자식 단위로 교체한다.
5. 자식 단위를 순서대로 생성한다.
6. 자식 중 하나가 다시 `MAX_TOKENS`이면 그 자식만 같은 방식으로 한 번 더 분할한다.
7. 허용 깊이 또는 호출 상한을 넘으면 상세 진단과 함께 실패한다.

잘린 응답 본문은 문장과 코드 블록이 불완전할 수 있으므로 최종 글에 포함하지 않는다. 여기서 결과 보존은 잘린 텍스트 보존이 아니라, 이미 정상 완료된 형제 단위와 섹션을 재생성하지 않는다는 의미다.

## 안전 상한

- 초기 하위 단위는 상위 섹션당 1~5개 범위에서 계획 모델이 결정한다.
- 재분할 최대 깊이는 2로 제한하며 `devnote.ai.gemini.max-split-depth=${GEMINI_MAX_SPLIT_DEPTH:2}`로 설정한다.
- 한 번의 재분할은 최소 2개의 자식 단위를 반환해야 한다.
- 전체 생성 단위 호출 수는 `devnote.ai.gemini.max-generation-calls=${GEMINI_MAX_GENERATION_CALLS:40}`으로 제한한다.
- 분할 계획이 비어 있거나 키가 중복되거나 부모와 같은 범위를 반복하면 즉시 실패한다.
- `SAFETY`, `RECITATION` 등 `MAX_TOKENS`가 아닌 종료 사유는 분할하지 않고 기존처럼 실패 처리한다.

상한은 글의 최종 길이를 제한하지 않는다. 모델이 끝없이 같은 범위를 재분할하는 상황만 차단한다.

## Markdown 조립

- 상위 섹션은 `##` 제목으로 유지한다.
- 초기 하위 단위가 여러 개면 `###` 제목과 본문을 계획 순서대로 배치한다.
- 초기 하위 단위가 하나뿐이면 중복 목차를 피하기 위해 그 단위의 `###` 제목을 생략한다.
- 재분할 자식은 필요할 때 `####` 제목까지 사용할 수 있다.
- 모든 완성 리프 노드를 깊이 우선 순서로 조립한다.
- 빈 본문, 닫히지 않은 코드 펜스, 마지막 미완결 문장은 검수 대상으로 전달한다.

## 검수와 선택적 수정

검수 결과는 상위 `sectionKey` 대신 실제 생성 단위의 `contentKey`를 가리킨다. 오류가 있는 리프 노드만 수정 프롬프트로 다시 생성한다.

수정 응답이 `MAX_TOKENS`이면 해당 리프 노드에도 동일한 재분할 규칙을 적용한다. 정상 완료된 다른 리프 노드는 유지한다. 두 번째 전체 검수에서도 오류가 남으면 기존 정책대로 게시글 생성을 실패 처리한다.

## 오류와 관측성

각 모델 호출에 다음 문맥을 로그로 남긴다.

- 단계: `PLAN`, `UNIT_GENERATION`, `UNIT_SPLIT`, `REPAIR`, `REVIEW`
- 상위 `sectionKey`
- 현재 `contentKey`
- 분할 깊이
- 시도 횟수
- 종료 사유
- 응답 문자 수
- 누적 생성 호출 수

최종 예외에는 최소한 단계, `contentKey`, 깊이, 종료 사유를 포함한다. 프롬프트 전문이나 API 키는 로그에 기록하지 않는다.

## 테스트 전략

- 여러 초기 하위 단위가 계획 순서대로 조립되는지 검증한다.
- 한 단위만 `MAX_TOKENS`일 때 정상 완료된 형제 단위가 다시 호출되지 않는지 검증한다.
- 재분할된 자식이 원래 위치에 조립되는지 검증한다.
- 재분할 자식 하나가 다시 잘릴 때 그 자식만 2차 분할되는지 검증한다.
- 최대 분할 깊이와 전체 호출 상한에서 진단 예외가 발생하는지 검증한다.
- 중복 키, 빈 분할 계획, 비정상 종료 사유를 거부하는지 검증한다.
- 검수 실패 리프만 수정되고 다른 리프 결과가 보존되는지 검증한다.
- 기존 HTTP 429 백오프와 최종 응답 DTO가 유지되는지 회귀 검증한다.

## 완료 조건

- 긴 섹션이 `MAX_TOKENS`에 도달해도 실패한 단위만 재분할해 생성을 계속한다.
- 정상 완료된 단위에 대한 Gemini 재호출이 발생하지 않는다.
- 최대 깊이와 호출 상한 안에서만 재귀 분할한다.
- 최종 결과가 유효한 순서의 Markdown으로 조립된다.
- 기존 API 요청과 응답 형식, 관리자 미리보기 흐름이 변경되지 않는다.
